1. Executive Summary & The Problem It Solves

The Industry Problem: When high-severity incidents strike modern distributed applications, mean time to detect and resolve (MTTD/MTTR) directly dictates downtime revenue losses. While Generative AI and LLMs have demonstrated remarkable diagnostic capabilities, engineering organizations strictly refuse to grant AI agents autonomous write-access to production infrastructure.

The root cause of this hesitation is legitimate: unconstrained LLMs hallucinate non-existent CLI flags, issue catastrophic shell commands (e.g. indiscriminate restarts, rm -rf), flap state unpredictably, and cannot be mathematically audited.

The SentinelLoop Solution: SentinelLoop bridges this trust deficit through a strict Dual-Layer Separation of Concerns. It isolates stochastic reasoning (LLM diagnosis) from deterministic enforcement (hard-coded safety guardrails).

Core Philosophy: "AI Diagnoses, Deterministic Rules Decide"
The LLM is treated as an untrusted advisory component. It proposes actions from a closed allow-list, but an unbypassable, air-gapped guardrail engine evaluates company policy before any physical change can touch the target service.

4. End-to-End System Architecture

SentinelLoop operates as a strict, cyclic Finite State Machine (FSM). It rejects unstructured free-form agent execution in favor of formal operational gates.

1. Perception Layer (Sensors)

Periodically polls target service endpoints (/health, /metrics, /logs, /deploys). Detects anomalies against SLA thresholds (p95 latency > 2000ms, error rate > 5%, CPU > 85%).

Automatically surfaces relevant Markdown operational runbooks from a local library to feed into the diagnosis context.

2. Diagnosis & Planning (Brain)

Invokes DeepSeek-V4-Flash via NVIDIA NIM. Constrained by rigid Pydantic JSON schemas and few-shot examples. Returns: root cause hypothesis, supporting evidence snippet, proposed action, and confidence (0.0 to 1.0).

Actions are strictly restricted to: restart, scale_up, scale_down, rollback, or noop.

3. Guardrail Engine (Safety Gate)

Zero LLM involvement. 100% hard-coded Python logic. Evaluates the proposed action against safety rules, operational history, and rate limits.

Emits one of three immutable decisions: AUTO_APPROVE, NEEDS_HUMAN_APPROVAL, or REJECTED.

4. Executor & Verification (Hands)

Sandboxed HTTP client. Cannot spawn subprocesses or execute shell commands. Only hits predefined endpoints on the toy service.

Performs mandatory verification polling. If service fails to recover after remediation, flags incident for human escalation.

5. The Core Innovation: Guardrail Engine Deep-Dive

The "Air-Gap" Architectural Invariant
agent/guardrail.py and agent/executor.py are prohibited by linting and unit tests from importing the LLM or OpenAI client. If the LLM experiences prompt injection, catastrophic drift, or hallucinations, the safety layer remains unaffected.
Rule # Trigger Condition Gate Outcome Operational Rationale
Rule 1: Confidence Floor confidence < 0.60 REJECTED Forces escalation to on-call engineer when AI is uncertain. Prevents guessing under noisy conditions.
Rule 2: High Blast-Radius Action is rollback NEEDS_HUMAN_APPROVAL Rollbacks risk data migrations and schema mismatches. A human must approve rollback actions.
Rule 3: Safe Low-Risk Action is restart (conf ≥ 0.6) AUTO_APPROVE Transient memory leaks or worker deadlocks benefit from rapid automated restart without waiting for human wakeup.
Rule 4: Rate Limiting Action is scale (> 3 per 10m) REJECTED (Rate Limited) Prevents runaway auto-scaling storms and cloud bill explosions during cascading traffic anomalies.
Rule 5: Anti-Flapping Gate Back-to-back action without VERIFY REJECTED Prohibits taking consecutive actions without verifying the health outcome of the previous mitigation first.

Key Benchmark Insights

1. Where the LLM Succeeded: For standard memory leaks, CPU thread starvation, and obvious deployment crashes, the LLM achieved near 100% accuracy and proposed instantaneous mitigation.

2. Where the LLM Struggled: In multi-variable scenarios (e.g. an upstream payment gateway timing out while CPU was concurrently high), the LLM suffered from "recency bias", diagnosing CPU overload instead of external dependency timeout.

3. The Guardrail Saved the Day: In 7 out of 7 misdiagnosed cases, the guardrail intercepted the LLM's low-confidence or dangerous action and either rejected it or escalated to a human.

7. Comprehensive Interview Playbook & Talking Points

Q1 "Can you walk me through this project from end to end?"

Recommended Answer Structure:

"SentinelLoop is an autonomous SRE agent I built to solve the trust problem with AI in infrastructure. Modern LLMs are great at analyzing telemetry, but they are too unpredictable to let run wild on production services. I designed a 6-stage finite state machine: Perceive, Diagnose, Plan, Gate, Act, and Verify."

"The agent monitors a microservice, collects logs and metrics, and when latency or error rates spike, feeds the telemetry and matching runbooks to an LLM via NVIDIA NIM. The LLM returns a structured JSON root-cause diagnosis and recommends one action from a closed allow-list. But before that action is touched, it must pass through my Guardrail Engine—a deterministic, rule-based gate written in pure Python. The guardrail enforces policies like confidence thresholds and mandatory human approvals for high-impact actions like rollbacks. Finally, an executor applies approved actions, verifies health, and writes an immutable audit trail."

Q2 "Why did you build a separate Guardrail Engine instead of prompting the LLM to follow safety rules?"

Recommended Answer:

"Relying on an LLM to police itself is an anti-pattern in production engineering. Prompted rules suffer from prompt injection, token length decay, and non-deterministic compliance. An LLM might follow a rule 95% of the time, but in SRE, a 5% failure rate means accidentally dropping production databases or triggering rolling restarts during peak traffic. By encoding safety invariants in deterministic code—with an enforced architectural import boundary preventing the guardrail from touching LLM code—we guarantee safety invariants with mathematical certainty."

Q3 "What were the biggest technical challenges you faced during implementation?"
  • Enforcing Strict JSON Schema Output: LLMs love to include conversational markdown wrappers. Solved this using Pydantic models with strict field validation, temperature 0, and fallback parsing.
  • State Management & Anti-Flapping: Preventing the agent from thrashing actions (e.g. scaling up and down repeatedly). Built sliding-window state tracking in the guardrail to rate-limit actions and require verification before follow-up actions.
  • Real-world Benchmark Ground Truth: Constructing 16 realistic scenarios with pre-committed ground truth to measure true diagnosis and safety gate performance honestly, without cherry-picked data.
